# Lessons from the other kexts, checked against this one

Everything that bit during the WCN7850 Wi-Fi bring-up (QwzMac / AirportWCN7850 history and notes, 2026-10-13 to 15) and the NVIDIA driver work, with what it means for QcaBluetooth. Checked 2026-10-16 against build `46e1de4e`.

| # | Lesson | Here |
|---|---|---|
| 1 | A `#define` renamed a function the kext itself defined (`explicit_bzero` → `bzero`), producing an exported self-recursive `_bzero`: every call overflowed the kernel stack, a double fault, a silent freeze or reset. | `build.sh` refuses a kext that defines any symbol the running kernel exports (same check as QwzMac). No macro in this kext renames a function. ✓ |
| 2 | Large objects on the kernel stack. | Biggest locals: a 200-byte log line, a 64-byte file name, the 20-byte version block. Transfer buffers come from `createIOBuffer`. ✓ |
| 3 | `IOCommandGate::runAction` passes the gate's owner, not the caller: NULL softc after a "successful" attach. | No gate, no workloop. N/A |
| 4 | Init ordering: a callback (`enable()`) ran on another thread before the object it used existed (watchdog created after `attachInterface`; softc allocated after the native layer wrote through it). | `thread_call` is allocated **before** `PMinit`/`registerPowerDriver`, so `setPowerState` can never see it missing; `setPowerState` also null-checks it. `registerService()` is the last thing `start()` does. ✓ (fixed this round) |
| 5 | Use after the owner went away: interrupt handler running on a reset chip; late teardown in `stop()` froze shutdown. | Interface pointer is retained while held; `stop()` uses `thread_call_cancel_wait`; the wake thread checks `isInactive()` on itself and the device; no interrupts, no MMIO, no shutdown hook needed (nothing runs after `start()` returns). ✓ (fixed this round) |
| 6 | DMA from memory the family did not expect (non-dmamem loads, missing syncs, >4 GB). | Both EP0 and bulk transfers use `IOUSBHostDevice::createIOBuffer` descriptors, prepared before use. Nothing from the stack goes to the USB family any more. ✓ (changed this round) |
| 7 | Verbose `IOLog` on the boot console (60 ms per line) stalled a time-critical bring-up. | About ten lines in total. ✓ |
| 8 | **OpenCore-injected kexts' `IOLog` lines never reach the unified log**; `sudo dmesg` and IORegistry properties are what you can read. A log ring published on the device as a property survived every freeze and found the root cause. | Every log line is appended to a 4 KiB ring published as the `Log` property; progress in `Stage`, result in `LastResult`, chip state in `RomVersion`/`PatchVersion`/`Status`. The bring-up doc now reads `ioreg` and `dmesg`, not `log show`. ✓ (added this round) |
| 9 | A 512 KB `OSString` property failed silently and looked frozen. | 4 KiB ring, capped, first lines kept. ✓ |
| 10 | Bisection without rebuilding: `qwz_stage=<n>` boot argument, one stage per boot; NVRAM runtime writes do not persist on this board, so the limit lives in the OpenCore config's boot-args. | `qcabt_stage=<n>`: 1 open + version read, 2 set configuration + pipe, 3 rampatch, 4 NVM; `-qcabtoff` disables matching. Both are boot-args in the USB config. ✓ (added this round) |
| 11 | Panics look like hard freezes with the NVIDIA driver; panic reports are never saved on this board; an NVRAM reset once erased the only report. Escape a boot loop with F11 → NVMe EFI, never by resetting NVRAM. Picking the NVMe macOS from the USB stick's OpenCore picker still injects the USB config's kexts. | Documented in [04-bringup.md](04-bringup.md). The kext's whole life is a couple of seconds inside `start()`; a freeze right after the USB enumerates the controller is this kext until proven otherwise. |
| 12 | OpenCore `Misc → Debug → Target 67` (file logging) makes USB boots crawl or black-screen at the picker; keep `0` on the stick. | I had copied `67` from the NVMe config onto the USB this morning; set back to `0`. The NVMe EFI keeps its own value. ✓ |
| 13 | Newer clang may emit `__cxa_atexit` for static destructors, which a kext cannot satisfy. | `nm -u` shows none; the statics are plain tables. ✓ |
| 14 | `build.sh` flake: `_kmod_info missing` on a first build after edits. | Same check is in this `build.sh`; it has not flaked here (three builds). Rebuild if it does. |
| 15 | Sleep/wake was never wired in the Wi-Fi driver; "don't let the Mac sleep during the first tests". | Wake path exists but is unverified and probably cannot open the device while `bluetoothd` holds it. Same advice for the first tests. |
| 16 | A wedged chip delayed the next boot; cut PSU power ~15 s after a freeze. | The Bluetooth chip keeps its RAM on standby power too: after a bad download, a cold start (PSU off) is the way to get the ROM state back. |
| 17 | Follow the reference implementation rather than guess (the taskq rewrite was a detour). | The USB sequence is IntelBluetoothFirmware's shape line by line (open, `setConfiguration` unconditional, child-iterator interface lookup, `copyPipe`, `io`, close, `FirmwareLoaded`, rename), and the protocol is `btusb.c`'s. Nothing invented. |

Not applicable here and why: PCI config space, MSI/INTx, bounce buffers, mbuf clusters, net80211 hooks, the command gate and `tsleep` (all Wi-Fi/PCIe stack).
